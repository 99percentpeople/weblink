# 文件传输流程与所有权

文件传输使用 [P2P 控制协议](p2p-protocol.md)中的类型化 RTC 控制协议，同时保留独立的二进制数据通道、压缩 worker 和缓存生命周期。UI 组件不构造文件控制消息，也不创建传输通道。

## 职责划分 {#responsibilities}

- `FileTransferService` 管理发送、共享、请求、重试、续传与暂停流程，通过依赖注入工作，不导入 UI 或 toast。它注册三个传入文件请求处理器，以及 RTC 通道、会话关闭观察器，随应用 provider 一起销毁。
- `TransferRegistry` 管理活动运行、通道、初始化、计时器、缓存租约与清理。内部按实际会话实例和逻辑文件 ID 索引运行，不仅使用全局文件 ID。
- `transfer-message-binding.ts` 将运行绑定到明确的消息 ID。每次事件都重新解析该 ID，因此删除较早的消息不会把进度误写到另一个数组元素。接收完成要等待缓存刷新和最终文件组装。
- `file-transfer-state.ts` 定义聊天、同步与任务视图共用的运行快照和选择器。任务列表不再从相同文件 ID 的最新消息猜测所有权。
- `transfer-service.ts` 提供应用专用工厂和适配器。`FileSender`、`FileReceiver`、包编码与压缩仍是核心实现细节。

Provider 保留呈现策略，包括错误 toast，以及现有公开 UI 方法，并将文件工作委托给服务。

## 身份与并发 {#identity-and-concurrency}

缓存文件、传输运行与聊天消息具有不同的身份。

每项活动运行都有独立 ID、所属 `PeerSession`、`fileId`、`messageId` 和传输器。两个 peer 可以同时读取、发送同一份完整缓存，不会替换彼此的运行或进度。同一会话、文件的第二个操作会被拒绝，不会破坏第一个。缓存写入准备在异步创建缓存之前预留；同一缓存不能有并发接收者，也不能在活动发送者读取期间重写。

只有该会话中预期接收通道的运行才能接受传入通道。未知、重复以及已退休会话的通道会关闭，没有全局无限增长的待处理通道缓冲区。一个提前抵达的通道可在其已知运行中等待缓存、worker 初始化；运行始终未就绪时，通道等待有明确上限。

线上控制消息、分块数据包以及现有 `<fileId>-0` 通道标签保持不变。这不意味着同一会话可以并行运行同一文件的多个传输。标签没有运行代次，因此不能单靠标签区分同一会话、文件组合中的两次历史尝试；增加这种区分需要单独修改线上协议。

## 可移植的文件传输契约 {#portable-file-transfer-wire-contract}

当前文件数据协议有意独立于可复用的控制协议。非 Web 客户端无需使用 IndexedDB、`FileSender`、`FileReceiver` 或 Web Worker，但必须精确实现以下通道与字节契约。

权威定义位于：

- `domain/transfer/protocol.ts`：JSON 控制帧与校验。
- `domain/transfer/packet.ts`：二进制块头编解码。
- `domain/protocol/messages.ts`：上层 `send-file`、`request-file` 和 `resume-file` 建立消息。

### 通道标识 {#channel-identity}

文件载荷通道使用：

- DataChannel protocol：`transfer`
- label：`<fileId>-0`

当前协议字符串对应**没有版本标记的旧线上格式**。未来不兼容的传输格式必须使用新的协议标识，不能悄悄改变 `transfer` 的含义。

Windows 原生房间适配器会在总大小不超过 256 KiB、数量不超过 32 条时，通过一次 IPC 把排队的二进制文件块交给 Rust；Rust 仍按原来的每条 DataChannel 消息逐块发送。单个块会立即发送，传输控制消息保留队列顺序。原生通道的 drain 通知继续驱动发送背压。

### JSON 控制帧 {#json-control-frames}

活动传输通道交换以下 JSON 帧：

```json
{ "type": "request-content", "ranges": [0, [2, 5], 9] }
{ "type": "complete" }
{ "type": "pause" }
```

范围项可以是单个非负分块索引，也可以是两端都包含的 `[start, end]`。

协议解析器仍接受 `request-head` 和 `head` 以兼容旧客户端；当前应用流程已通过上层控制协议交换文件元数据，不会主动使用这两种帧。

### 二进制块数据包 {#binary-block-packet}

文件字节以二进制数据包发送，使用固定的 **7 字节头**：

| 字节范围 | 编码         | 含义                                       |
| -------- | ------------ | ------------------------------------------ |
| 0..3     | uint32，大端 | 分块索引                                   |
| 4..5     | uint16，大端 | 压缩分块内的块索引                         |
| 6        | uint8        | `0` 或 `1`，表示是否为该压缩分块的最后一块 |
| 7..      | bytes        | 压缩块载荷                                 |

发送方先使用 `fflate.deflateSync` 所采用的 raw DEFLATE 格式压缩每个逻辑分块，再把压缩字节序列拆成块。接收方按 `chunkIndex` / `blockIndex` 收集数据块，拼接到标记为 `isLastBlock` 的块，再按 raw DEFLATE 语义解压完整压缩分块，最后写入原始分块字节。

压缩等级由发送方本地选择，不编码到线上数据中。等级 0 仍是合法的 DEFLATE 流，因此其他客户端必须解码 raw DEFLATE，不能依赖生成它时使用的压缩等级。

块索引使用 uint16，因此一个压缩分块最多有 65,536 个可寻址块位置。当前 Web 发送方的默认块大小远大于普通配置分块尺寸所需的最小值，但其他实现仍须遵守 uint16 上限。

### 跨客户端实现规则 {#cross-client-implementation-rules}

兼容的非 Web 发送方、接收方应遵循：

1. 完成上层 `send-file` / `request-file` 控制交换后，才赋予传输通道载荷语义。
2. 对这一旧格式精确使用 `transfer` 协议名和 `<fileId>-0` 标签。
3. 分块范围包含两端，续传时保留逻辑分块索引。
4. 整数采用大端编码，使用上述 7 字节头。
5. 每个完整逻辑分块先做 raw DEFLATE，再拆成块。
6. 重组完整压缩分块后再解压。
7. `complete` 仅表示传输通道完成，不表示接收客户端已持久完成缓存或文件提交。
8. `pause` 表示有意关闭通道，并保留可续传的缓存分块。
9. 拒绝格式错误的 JSON 控制帧和无效二进制头，不把它们解释为载荷数据。

`apps/web/test/unit/file-transfer-protocol.test.ts` 中的单元覆盖锁定 JSON 结构、范围校验与精确的字节级头编码。

## 取消与最终提交 {#cancellation-and-finalization}

`sendFile`、`shareFile` 和 `requestFile` 在控制交换及传输建立后 resolve，不会等待整个文件传完。最终完成状态应观察消息或任务。取消待处理文件请求会留下可续传的暂停状态，而非发送失败。取消不会撤回已发送字节，也不会丢弃已经缓存的分块。

会话关闭和应用离开会取消进行中的准备操作并销毁所属运行。迟到结果在附加通道或继续流程前，必须核对操作与运行所有者。无法中止的迟到 `createChannel()` 结果会被关闭。发送、接收初始化在异步工作后检查关闭状态，避免关闭后继续附加 worker。

注册表清理会先移除所有权，再调用关闭回调，因此重入或延迟事件不会移除替代运行。订阅和计时器属于运行。UI 卸载不会停止应用拥有的传输。

接收最终完成意味着缓存刷新和文件组装已结束，不只是最后一个数据帧抵达。迟到的组装结果不能把已退休运行的消息标记为完成。刷新和组装失败会记录在关联文件消息上。

共享缓存同时由活动运行和准备操作保留。自动删除会等待租约释放、已注册交付完成。暂停或失败的交付保留缓存，不受哪个 peer 先完成的影响；同一交付成功重试或续传后才释放这一要求。用户显式删除缓存与自动删除是不同操作，会停止受影响的活动运行。

## 本地共享与目录任务 {#local-sharing-and-directory-tasks}

共享状态属于本地内容记录，因此相同字节及其所有聊天引用都投影同一个 `isShared` 值。导入、新接收字节和升级前缓存默认私有；重复导入或接收保留现有本地状态。远端元数据永远不能控制这个标记。

新的私聊、房间、转发或从文件库选择的发送，会在文件准备和本地消息创建完成后、网络交付前开启共享。重试与续传保留当前标记，后续网络失败不会撤销新发送的共享选择。独立保留引用让共享字节在消息删除和自动附件清理后继续存在。取消共享保留本地字节；显式删除移除所有引用及目录项。共享列表属于本机，跨房间持久保留。

本地共享文件标题栏可添加已有文件库文件，或导入本地文件、文件夹。此类显式添加只在导入成功后开启共享；文件夹沿用应用现有 ZIP 打包流程。普通文件库导入仍保持私有。目录行与任务列表观察同一下载任务，包括进度、暂停、续传、取消和完成，因此返回某成员列表时可恢复当前传输状态。
刷新期间保留当前行和选择，直到新分页抵达；权限重新验证前，旧行不可下载。取消是终止状态，会移除该接收的部分缓存与文件引用；暂停保留部分数据以便续传。取消一个接收者时，仍有其他已授权接收者需要的来源会继续保留，待其他接收者完成或脱离后才释放已取消引用；其他本地引用不受影响。再次获取已取消文件会创建新任务。
完整本地内容按指纹匹配，即使远端 ID 或名称不同，目录行也会显示已获取，批量选择会跳过它，服务调用不会创建额外任务或引用。删除本地内容后才可重新获取。

目录获取使用 `shared-files-v1`，以及 [P2P 控制协议](p2p-protocol.md)中的版本 3 目录契约。目录任务生命周期独立于消息绑定，但共用传输注册表、验证、范围续传与内容接收协调器。已有且验证过的本地内容不需要远程请求；新传输或续传始终检查当前远端权限。关闭或切换侧栏会取消目录请求，不取消已经开始的传输。目录任务保留到应用会话结束，已完成的本地文件持久存于 IndexedDB。
