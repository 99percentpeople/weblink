# 设备配对与内容权限

每个本地浏览器配置或桌面 WebView 配置在 IndexedDB 中持有一个 ECDSA P-256 私钥，用于信令所有权证明和连接绑定。优先使用 Web Crypto 创建不可导出的原生密钥，并在持久化新密钥对前检查公钥导出与签名能力。当 API 或算法不可用时，包括局域网 HTTP 环境，按需加载的 Noble 实现会提供 P-256、SHA-256 和 HMAC-SHA-256，保持公钥、签名与凭据格式一致。软件密钥字节存于同一配置的 IndexedDB；Web Crypto 恢复可用后也能使用这些字节。随机数始终来自 `crypto.getRandomValues`。无效数据和验证失败不会触发回退。如果 Web Crypto 变得不可用，会保留现有不可导出的原生密钥，不会转换或悄悄替换。这种兼容能力不会让 HTTP 成为其他浏览器 API 所要求的安全上下文。

已配对设备还会互相签发配对密钥。这些密钥直接用于 peer 身份验证，不是单独的恢复令牌。设备身份独立于账号身份、本地 MCP bearer token 和临时自动化 scope 授权。项目没有 SSO，也不会在整个账号范围传播信任。

专用有序 RTC 通道 `weblink-device-identity/1` 交换公钥，并对双方设备 ID、新挑战值以及双方连接的 DTLS 证书指纹签名，以证明持有私钥。首次配对记录 SHA-256 公钥指纹；后续连接针对相同的新鲜握手记录，证明持有已交换的配对密钥。名称、client ID 或仅知晓公钥都不能自动获得权限。
首次使用时，若设备没有保存公钥固定记录、配对密钥或隔离记录，会在验证新签名证明并存储公钥固定记录后自动配对。双方将配对历史状态纳入签名记录。只要任一端还记得共享密钥交换或隔离状态，另一端即使本地记录全无，也不能按首次使用处理：必须有双方仍持有的公共密钥、经验证的身份恢复，或显式修复。首次密钥交换前保存的匹配公钥固定记录仍可恢复该中断交换。配对密钥连接要求已签名的历史和身份恢复协商，缺失协商字段不会开启回退。
首次接纳依赖房间访问，包括已配置的房间密码，并信任第一次遇到且验证通过的密钥。之后的自动连接必须证明与已保存身份的连续性。

手动修复使用单独的有序 RTC 通道 `weblink-device-pairing/1`。一端请求配对，另一端通过通知或设备权限设置明确接受或拒绝。批准前没有比对码或私钥挑战，因此自动身份握手失败不会阻止手动修复。接受表示替换当前连接保存的身份决定，不表示自动证明旧身份。连接中交换的公钥会固定保存，供后续恢复使用。双方都必须保存决定后才能开启实时权限，随后开始现有的签名凭据签发和续期流程。

请求绑定当前会话与随机请求 ID，60 秒后过期。取消、拒绝、超时或断开都会使批准操作失效。接收方生成自己的本地操作 ID，因此复用远端请求 ID 不能重新激活旧通知的批准按钮。仅发出请求不会改变已保存密钥或权限，即使接收方仍信任请求方也是如此。同时发生或重复的请求不能替换活动请求。手动修复被接受前发起的自动证明回调不能覆盖新决定。重连和自动恢复仍需新的身份、共享密钥证明；手动确认不会为冒充者增加自动回退路径。

没有仍可验证的配对密钥或经验证的身份恢复时，身份不匹配或远端证明无效会使设备处于**不受信任**状态。信令和 RTC 连接仍可用于发现与配对，但拒绝所有应用权限，并取消当前传输、剪贴板活动、输入和 peer 自动化。设备进入隔离状态时会重置已有权限选择。持续的应用内警告可打开该设备的权限设置，但警告本身不授予权限；重复状态更新不会重复弹警告，修复或断开会关闭它。
已隔离的记忆密钥不能在后续重连时自动恢复信任。显式重新配对会替换公钥固定记录并恢复默认权限；自动首次配对也采用相同默认值：开启接收内容、共享屏幕和提供文件列表，远程控制与自动化需要批准。这不会启动屏幕采集，也不会绕过操作系统采集同意。必须先成功保存密钥，设备才能受信任。
正常断开、握手截止或本地存储、传输错误会撤回实时权限，但不会隔离记忆密钥或清除保存的权限，即使错误发生在验证完成之前也一样。消息通道可用时，发起设备会重试握手。重连必须提供新的证明，之后才能再次应用已保存设备权限。

## 配对密钥与自动续期 {#pairing-keys-and-automatic-renewal}

双方建立信任后，各自独立生成一个 256 位随机共享密钥，通过已验证的 DTLS 通道发送给对方；签发方保留同一密钥作为验证材料。重连使用 HMAC-SHA-256 挑战证明，不传输秘密本身。证明绑定双方设备 ID、新 nonce、公钥和 DTLS 指纹，不能复用于另一条连接，也不能反射到相反方向。本地 ECDSA 签名私钥从不发送给另一设备。

配对密钥只有**已签发**与**已接收**两类，替换期间另有临时待签发记录。任一共享方向都能验证连接。如果签发记录、公钥固定记录或本地身份密钥对丢失，但双方还保留一把匹配的共享密钥，就会自动恢复信任、保留权限设置，并替换缺失的签发记录。若接收方丢失了已接收副本，签发方会在身份验证后发现，并采用相同替换流程。本地身份密钥对只剩一部分时，加载过程会重新生成密钥对，不删除 peer 密钥。公钥固定记录与已签发、已接收密钥分别存储，丢失公钥记录不会删除已接收密钥。

每把配对密钥都要求签发方签名，将密钥 ID、到期时间和秘密的 SHA-256 哈希绑定到双方设备 ID 及双方身份公钥。这是现有凭据上的公开元数据，不是新令牌，也不是身份私钥副本。仍存活的共享密钥验证了重新生成的签名身份后，正常维护流程会把配对密钥重新绑定到该身份。待处理 offer 在此过程中保留秘密，避免 ACK 丢失导致待处理密钥被丢弃。

若一端丢失所有 peer 记录，但保留原身份密钥对，仍记得它的另一端会使用保存的公钥固定记录验证新连接签名。反方向上，记忆端出示遗忘端此前签发密钥上的已签名绑定。遗忘端验证自己原来的签名，并要求绑定中的接收者身份与 peer 的新连接证明一致。本地保留的签发记录同样能恢复缺失的 peer 公钥固定记录。当前公钥固定记录若与历史绑定冲突，以当前记录为准。双方都不会仅因为对方声称“记得自己”而信任；历史绑定本身也不能验证其他设备或重放连接签名。

身份恢复是显式且带签名的协商：至少一端必须没有配对密钥，双方都不能声明隔离，且双方都要支持该扩展。恢复状态纳入同一个绑定 nonce 与 DTLS 的握手记录。绑定格式错误或已知密钥的 MAC 错误属于验证失败，绝不是回退至身份恢复的理由。证明中不发送恢复秘密。验证并持久保存公钥固定记录后，现有签发与 ACK 流程会恢复缺失密钥，不重置权限选择。恢复中断和存储写入失败可以重试，期间继续按适用规则限制实时应用访问。

若身份密钥对也已丢失，且没有双方共有的配对密钥，则必须显式修复。如果双方都保留公钥固定记录，即使都没有签发记录，身份恢复仍可替换缺失密钥。配对密钥格式仍在开发中，不支持未签名密钥，也不支持省略身份绑定协商的 peer。

默认续期间隔为 90 天，以签发方时钟计算。到期是续期截止时间，不是离线撤销：替换完成前，旧密钥仍可用于新的证明。签发方在重连或连接期间到达截止时间时续期，发送前先持久保存待处理密钥；接收方也必须保存后才确认。只有该确认才会淘汰旧签发记录。确认丢失、重启或存储写入失败会保留旧材料与待处理材料，并重试同一把待处理密钥。自动维护成功不会重置权限。

为某个 peer 启用配对密钥后，除显式协商的身份恢复路径外，公钥固定记录不能绕过缺失或无效的配对密钥证明。省略任一扩展也不能开启恢复路径。已确认的公钥固定记录可恢复首次交换；本地信任与 peer 同意建立前不会开始交换。未送达的首次 offer 可用已固定的签名身份恢复。
收到密钥或签发确认时，持久化密钥与将“配对密钥认证或经验证的身份恢复”设为强制要求是原子操作。之后删除密钥也不会清除此要求。显式重新配对会原子记录新确认并删除旧配对密钥；提交过程中连接断开，不能激活陈旧的实时权限，也不能撤销有效的已保存确认。显式隔离的密钥不能自动恢复。手动重新配对会清除旧配对密钥，恢复默认权限，而非以前的永久授权。
若共享密钥与原绑定身份都无法验证，仍须手动重新配对。到期不提供强制撤销期限；显式隔离或重新配对才会撤销旧密钥。

每台设备具有以下设置：

- **接收内容：** 一个开关统一限制所有传入应用内容，包括消息、资料、文件、文件列表、剪贴板、音视频、测速、远程操作和自动化。关闭后仅保留传输、能力发现及身份、配对流量；应用通道关闭，待处理请求取消。媒体立即从应用视图和录制来源中移除。接收轨道被禁用，重新允许接收后可复用；发送方收到接收能力更新后也会撤回媒体。这不能阻止恶意 peer 向已建立的网络传输发送数据包。
- **共享屏幕：** 控制向此设备发布本地屏幕、摄像头和音频，包括原生屏幕发布。远程屏幕、控制自动化也需要这一权限。关闭时会中断 peer 自动化，使已经批准的屏幕操作不能保留旧授权。
- **远程控制：** 询问、永久允许或拒绝。接收内容和共享屏幕必须同时开启。只有已证明配对身份的设备才能使用已保存策略。
- **提供文件列表：** 在接收权限之外，进一步控制共享文件目录；默认权限集中开启。

文件传输、控制、剪贴板和原生流媒体使用双向协议；即使本机是发起方，关闭接收也会中断这些交换。本地 MCP token 仍按自己的规则使用，远程设备配对不会签发、修改或撤销它们。

## 重复 ID 与信令部署 {#duplicate-ids-and-signaling-deployment}

Bun 信令和 Cloudflare Worker 都会签发新的 WebSocket 挑战。加入证明对挑战、client ID 和创建时间签名。已验证签名密钥的房间成员，只能被使用同一公钥的有效证明替换或恢复。未签名、错误密钥或重放的同 ID 加入请求都不能替换该成员或关闭其 socket。被拒绝的重复候选端会采用有上限的指数退避和新加入证明等待重试，即使它从未成功加入。等待期间的暂时传输失败仍会重试，离开房间会取消等待。任何重试都不发送 leave，也不覆盖当前所有者。只有已签名成员关系或租约消失后，不同签名密钥才能加入该 ID。已经接纳但被显式替换的会话仍会停止重试，防止接管循环。这保护当前已接纳设备，但服务器无法在某个未使用 ID 首次接纳前确定其所有权，端点配对仍然必要。

未签名的旧成员保留原有同 ID 替换和恢复行为，包括断线宽限期内缓存信令。旧客户端之间无需实现身份证明即可通信。提供无效证明会被拒绝，不会按旧客户端处理。有效的签名替换会将未签名成员升级；后续未签名加入不能降级或替换它。未签名成员仍受旧协议在 ID 冒充防护方面的限制。

使用 Redis 的 Bun 部署会跨节点原子预留房间、客户端租约。另一节点上存在已签名活动租约时，即使密钥匹配也保守拒绝；已签名重连应使用粘性路由。未签名租约可为旧客户端重连在节点间移动；旧传输退出时不会发出过期 leave 或释放新租约。新节点确认一次全新加入，使客户端重建信令状态。节点故障后，其他节点需等待租约过期才能接纳该 ID，期限为心跳超时 + 断线宽限期 + 心跳间隔 + 10 秒。Redis 故障会拒绝接纳和转发，不会绕过所有权检查。依赖此保护前须更新所有节点；混用版本不具备一致的接纳边界。

旧客户端可加入和恢复未签名成员关系，但不能通过设备配对、与新客户端交换应用内容，或在没有匹配证明时替换已签名成员。旧信令服务器不防护重复 ID 驱逐。持久 WebCrypto 密钥应使用 HTTPS、localhost 或桌面安全源。
清空整个配置存储会删除双向配对密钥，该配置会把 peer 当作新设备；仍记得旧身份的 peer 在没有共同密钥时仍要求手动重新配对。部分身份丢失后的信任恢复不会绕过信令所有权：不同签名密钥不能驱逐当前已连接的同 ID 成员，必须等待其离开或租约到期，客户端会在等待期间自动重试。配对密钥续期不会改变信令签名密钥。项目没有密钥备份或导出 UI。
